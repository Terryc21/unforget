## New for v0.3 (proposals from v0.2 retrospective)

These came out of a 2026-05-02 conversation about whether `/schedule` (Claude Code's remote-agent scheduling skill) should be integrated into unforget. The conclusion was no: integration would break the "any editor, any AI, any project" portability that makes unforget's pitch work, would couple adopters to Claude Code, and would create invisible failure modes when external scheduling breaks. But the underlying need (time-bound deferrals and external scheduling) is real. The two items below address that need without coupling unforget to any scheduler.

### T1: `Wake-up` field for time-bound deferrals

**Status:** Proposal

**Problem.** Today, a row that's dead until a future date (vendor reapplication window opens 2026-08-01, soak period ends after build 35, partner integration blocked until contract renewal) has no clean place to record the wake-up date. Users put it in the Finding cell as prose, in a footnote, or in a memory file that disappears at session end. None of those surfaces are queryable.

**Proposed shape.** An optional `Wake-up` field for rows that are time-bound. Two presentation options:

**Option A: detail-block field (recommended).** Lives in the detail block beneath the row, leaves the 10-column rating table unchanged.

```markdown
<details>
<summary>12 · Re-evaluate Best Buy API · 🌫️ SOMEDAY</summary>

**Wake-up:** 2026-08-01 (reapplication window opens)
**Closure pointer:** when reapplied, log the new ticket here.

The original application was rejected 2026-04-27. Reopen window closes 2026-05-07
(handled separately in the row above) but the next reapplication window starts 2026-08-01.
</details>
```

**Option B: 11th column.** Adds a `Wake-up` column to the rating table. Rejected for the same reason custom column reordering is rejected in `## Anti-patterns`: it expands the universal format and breaks comparability across projects that don't use it.

Recommend Option A. It's opt-in, doesn't bloat the table, and rows without a wake-up date are completely unaffected.

**Behavioral hook.** `/unforget scan` gains an awareness of the field:
- Rows with `Wake-up:` set to a date in the past are flagged as "woken" (default Recommendation: `investigate`).
- Rows with `Wake-up:` set to a future date are skipped from staleness checks (the row isn't stale; it's intentionally dormant).
- `/unforget scan --woken` shows only rows whose Wake-up date has passed, as a focused view for the weekly "what woke up this week?" ritual.

**What this does NOT do.** It does NOT fire any alert, schedule any agent, or push any notification. The Wake-up field is data the user reads when they choose to. External schedulers (see T2) handle the push side.

**Why this is the right shape for the public skill.** It's pure format work. Any AI tool that reads UNFORGET.md (Cursor, Aider, GitHub Copilot reading project docs) sees a date in a labeled field; it's parseable without unforget-specific tooling. No scheduler dependency, no Claude Code lock-in.

**Open questions for v0.3 design.**
1. Date format: ISO 8601 (`2026-08-01`) only, or also accept relative phrases (`+90 days`, `after build 35`)? Recommend ISO 8601 only for v0.3. Relative phrases are ambiguous without a reference date and harder for non-Claude AI tools to interpret.
2. Multiple wake-ups: can a row have a list of dates (e.g., quarterly check-ins)? Recommend single date only for v0.3. Recurring check-ins should be expressed as a `/schedule` cron externally, not in the row.
3. What if a wake-up date passes and the user doesn't act? The row stays in its current Target (typically `🌫️ SOMEDAY`); scan keeps surfacing it as woken until the user resolves it.

### T2: README "Recipes" section: scheduling unforget scans externally

**Status:** Proposal

**Problem.** Adopters routinely ask "how do I get reminded about deferred work without having to remember to run `/unforget scan`?" Today the README's only answer is the one-line note in `## Scheduling` ("`/unforget scan` is safe to run on demand. For automated recurring scans, the user can schedule it via Claude Code's `/schedule` skill or any cron-like external scheduler"). That sentence is correct but doesn't show the user how. Adopters interpret the silence as "you're on your own" and either build something fragile or stop thinking about it.

**Proposed shape.** Add a `## Recipes` section to README.md with worked examples for the most common external schedulers. Each recipe is a short paragraph plus a code block. The section should be neutral about which scheduler is best; the message is "pick whichever you already trust."

**Recipes to include in v0.3.**

1. **Claude Code `/schedule` (one-time wake-up).** For T1-style time-bound deferrals: `/schedule "run /unforget scan --woken and report rows that woke up" run_once_at: 2026-08-01T17:00:00Z`. Code-block example. Note that this requires Claude Code with `/schedule` configured.

2. **Claude Code `/schedule` (recurring weekly scan).** `/schedule "run /unforget scan and email me anything stale" cron: 0 14 * * 1` for Monday 2pm. Same caveats.

3. **GitHub Actions (recurring scan posted as issue comment).** A `.github/workflows/unforget-scan.yml` snippet that runs weekly, invokes the scan via Claude API or a CLI wrapper, and posts the result to a tracking issue. The wrapper does not exist yet (open question below); for v0.3 the recipe shows the workflow shape and links to the API call form.

4. **Plain cron + script.** A bash one-liner the user can drop into `~/Library/LaunchAgents/` (macOS) or `crontab` (Linux) that runs `claude-code` headless against the project, captures output, and emails or files-it-somewhere. This is the maximum-portability recipe.

5. **Linear / Jira due dates.** Not a scheduler per se, but the most common pattern in practice: when adding a row with a Wake-up date in unforget, also create a Linear issue with the same due date. The user reviews their Linear inbox weekly and the row resurfaces there. Recipe is a workflow note, not a code block.

**What this section deliberately does NOT do.** It does NOT recommend one scheduler. It does NOT integrate any of them into unforget. It does NOT create a hidden dependency. The Recipes section is pure documentation; deleting it would not break any installed unforget. It exists to show adopters what the external-scheduling pattern looks like, then get out of the way.

**Why this is the right shape for the public skill.** It strengthens the "unforget is the format, use any scheduler you want" pitch by making that statement actionable. Adopters bounce off "use any external scheduler" when no example is given; they adopt confidently when they see five working examples for the schedulers they already use.

**Open questions for v0.3 design.**
1. Does a `claude-code --headless --skill unforget --command scan` CLI form exist? If not, recipe 3 (GitHub Actions) and recipe 4 (plain cron) need a different invocation path. Confirm before drafting the recipes for real. If headless invocation isn't possible yet, recipes 3 and 4 reduce to "open Claude Code manually on a recurring reminder" which is much weaker.
2. Should the Recipes section live in README.md or in a separate `docs/RECIPES.md`? README is more discoverable; separate file keeps README short. Recommend README inline for v0.3 (3-5 recipes is small enough), promote to separate file in v0.4 if the section grows past 8 recipes.

### U1: ~~document the non-zero exit contract; add `--exit-zero`~~ — ❌ WITHDRAWN

**Status:** Withdrawn 2026-07-31, same session it was proposed. **The premise was false.**

The exit-code contract is already documented in THREE places:
`scripts/verify_ledger.py:45-48` (module docstring), `reference/verify.md:67-68`
("**Exit 0** = gate passes … **Exit 1** = gate FAILS … **Exit 2** = usage error"), and
`scripts/README.md`. The documentation is correct, complete, and easy to find.

**What actually happened.** The operator chained the command with `&& echo ok`, saw the
failure branch on a legitimate `gate_pass: false`, and inferred the tool was broken —
without reading any of the three places that explain it. That is a reading failure, not a
documentation gap. Recorded here rather than deleted so the next person proposing this
item finds the answer instead of re-proposing it.

**Residual (genuinely small).** `--exit-zero` for advisory/reporting runs is still a mild
convenience for CI, but with the contract documented it is a nice-to-have, not a fix.
Folded into U4 as low-priority polish; not tracked separately.

### U6: `ROW_ID_RE` was too narrow — rows invisible to every check ⚠️ CRITICAL

**Status:** ✅ Implemented 2026-07-31. **Found while building U5, and worse than U5.**

**Problem.** `ROW_ID_RE = ^\|\s*([A-Za-z]?\d+)\s*\|` accepted at most ONE leading letter
and no suffix. Real ids in the field that it silently skipped:

| id | shape | consequence |
|---|---|---|
| `A48a`, `A48b` | letter suffix (a finding split into sub-rows) | **two 🔴 THIS ship-blockers excluded from the release gate** |
| `MI-08`, `MI-18` | hyphenated prefix (scoped sibling ledger) | **an ENTIRE ledger reported `rows_checked: 0`** while looking healthy |
| `**S12**` | bold-wrapped id | row skipped |

A row the regex does not match is invisible to *every* check: contradiction, tier,
this-blocker, char-budget, stale-recipe. The gate reported **2 blockers where 4 existed**,
and reported them as a clean, confident number.

This is the worst failure mode the tool has. It does not miss quietly; it asserts "clear"
over a blocker. A ledger can look perfectly healthy while hiding release-stopping work.

**Fix.** Grammar widened to `\*{0,2}((?:[A-Za-z]{1,3}-?)?\d+[a-z]?)\*{0,2}` — optional
bold, optional 1-3 letter prefix with optional hyphen, digits, optional letter suffix. The
prefix stays optional so bare-numeric ids (`| 1 |`, used by this file's own rating tables)
keep matching. Header and separator rows still correctly fail to match.

**Measured effect** on the Stuffolio installation:

| ledger | rows_checked before | after |
|---|---|---|
| UNFORGET.md | 49 | **51** |
| TERRY-UNFORGET.md | 0 | **41** |
| MI-UNFORGET.md | 0 | **7** |

Errors went 2 → 5: the two hidden blockers (A48a, A48b) plus a genuine status/narration
contradiction in A48a that no one had ever seen.

**Release readiness (assessed 2026-07-31).** Tested against every ledger reachable on the
author's machine:

| target | rows_checked | errors | note |
|---|---|---|---|
| `tests/fixtures/sample-project/` | 4 | 0 | unaffected — ids are `A1 P1 S1 U1`, none use the U6 shapes |
| `examples/UNFORGET.md` (shipped example) | 19 | 0 | clean; 1 advisory `this-blocker` warn |
| The Honest Machine (`~/The Honest Machine/UNFORGET.md`) | 0 | 0 | correctly 0 — that ledger is PROSE-format, zero table rows |
| Stuffolio UNFORGET / TERRY / MI | 51 / 41 / 7 | 5 / 0 / 0 | discovery site; was 49 / **0** / **0** |

Note **why the bug survived to production**: the fixture project exercises none of the U6
id shapes (no suffix, no hyphen, no bold), so the golden bench had no case that could fail.
`tests/test_row_visibility.py` closes that gap and builds its own fixture rather than
extending the shared one.

**Residual risk, stated honestly.** The change is strictly WIDER, so every previously-matching
row still matches and no existing behaviour is removed. The unknown is the other direction:
a ledger in the wild might contain a line like `| Note1 |` or `| 2026 |` that was previously
skipped as prose and is now parsed as a row. The negative tests cover headers, separators,
and column-name rows; they cannot cover every convention in the field.

That risk was judged acceptable for release: a spurious extra row surfaces IMMEDIATELY and
visibly (an odd entry in `list` output), whereas the bug being fixed is a SILENT false
negative in a release gate — the lint reporting "2 blockers" over a ledger holding 4. A
loud, cosmetic wrong answer is strictly preferable to a quiet, confident one. Ship.

**Side observation (not this item, logged for later):** a PROSE-format ledger like The
Honest Machine's receives no integrity checking at all, and `rows_checked: 0` is
indistinguishable at a glance from "invisible rows" — which is exactly how U6 presented.
Worth a future proposal: have `verify` distinguish "no table rows found" from "0 rows
matched" and say so.

**Regression guard.** `tests/test_row_visibility.py`, wired into `tests/run.sh`. Verified to
FAIL (6 assertions, naming A48a/A48b/MI-08 specifically) when the old regex is restored, and
to exit 1 so CI catches it. A test that has not been watched to fail is not a test.

### U2: `**Last verified:**` line in the ledger header

**Status:** Proposal · **recommended first**

**Problem.** Stuffolio's ledger had been format v2 since 2026-07-26 with `verify` available
and documented in the project's CLAUDE.md as gating archive/promote. It was never run. 113
findings, including 2 genuine release blockers, sat unseen. Nothing about the file looked
wrong, because the format has no notion of when it was last checked.

The format already solves this exact problem for a sibling concern: `**Last promoted:**`
makes a stale promotion visible on any read. Verification has no equivalent.

**Proposed shape.** On every `verify` run, write or update a header line:

```markdown
**Last verified:** 2026-07-31 — 2 errors, 83 warnings (gate FAILS)
```

Absent line = never verified. Old date = stale. Both readable at a glance, by a human or an
assistant, without running anything. Pairs naturally with U3: `archive`/`promote` can read
the line and refuse on a missing or stale one.

**Open question.** Should `verify` write to the file at all? It is documented read-only
today. Options: (a) relax to "read-only except its own header line"; (b) require an explicit
`--stamp` flag; (c) have `archive`/`promote` write it instead, since those already mutate.
Leaning (b) — preserves the read-only guarantee, keeps stamping deliberate.

### U3: enforce the archive/promote gate in CODE, not only in prose

**Status:** Proposal · ⚠️ **rewritten 2026-07-31** — the original framing ("nothing enforces
it") was WRONG and is corrected below.

**What the original proposal got wrong.** It claimed the gate was merely advisory. It is
not: `reference/promotion.md:74` specifies it as step 0 of the promotion ritual, in
unambiguous terms — *"If it reports any error-severity finding … **STOP.** You cannot make
a release decision over a ledger whose 'done' claims aren't trustworthy."* `reference/
commands.md:412` carries the equivalent step for `archive`. The specification is complete
and correct.

**The real, narrower finding.** The gate is **procedural** — prose an operator must read in
the right reference file at the right moment. In the field session the operator archived 16
rows without running verify, not because the rule was missing but because the rule lives in
a file that was never opened during that task. A prose gate is skippable by anyone who does
not consult it, and skipping leaves no trace.

**Proposed shape.** Have the `archive` and `promote` implementations *call* `verify_ledger`
rather than instructing a human to. Refuse on `error_count > 0`, printing the offending row
IDs. `--force` overrides and records the override in the ledger header (pairs with U2's
`**Last verified:**` line) so a forced run is auditable.

**Honest counter-argument, worth weighing before building.** unforget is a
*skill*, not a binary: much of it is executed by an assistant following reference prose, so
"enforce in code" only reaches the paths that actually run Python. If `archive` is largely
assistant-driven, the durable fix may instead be to make step 0 impossible to miss — e.g.
have `verify` write U2's header line, so an unverified ledger is visibly unverified at the
top of the file the assistant is already reading. That is cheaper than restructuring both
commands and does not depend on which code path runs.

**Recommendation:** build U2 first, then re-evaluate whether U3 is still needed. U2 may
subsume it.

**Check before implementing.** A ledger whose only error IS the row being archived away
must not deadlock. `--force` covers it, but the refusal message should name that escape
hatch explicitly.

### U4: `row_budget split` auto-headline truncates mid-phrase

**Status:** Proposal

**Problem.** `split` is otherwise excellent: five splits in the field session, all lossless,
all verified. But the auto-derived index headline cuts at a character budget with no regard
for clause boundaries. A real example, from a 7,629-character row:

```
macOS + iPad App Store MARKETING screenshots not captured (blocks macOS submit → see detail block
```

The parenthesis never closes and the sentence dangles. The operator supplied `--headline`
by hand for all five splits.

**Proposed shape.** Truncate at the last clause boundary (sentence end, em dash, or closing
parenthesis) before the budget; failing that, require `--headline` rather than emitting a
fragment. A dangling index row is worse than a refusal, because it silently degrades the
one line a reader scans.

### U5: `cell-count` check

**Status:** ✅ Implemented 2026-07-31 (`verify_ledger.py` check 10). Building it surfaced [U6](#u6-row_id_re-was-too-narrow--rows-invisible-to-every-check--critical), which was more severe.

**Problem.** SKILL.md line 177 already documents that embedded pipes shift the Status column
and that the fix was to locate Status by position rather than take the last cell. The parsing
code is fixed; the *data* is not guarded. The field session hit this three times:

1. Archive row `S6` — 11 cells (an embedded pipe in prose)
2. Archive row `U1` — 12 cells (same cause)
3. Live row `A48b` — 11 cells, **created during the session** by a `verify-still-open` recipe
   containing `grep -c 'InventoryResolver\|localDefault'`, whose `\|` Markdown read as a
   column separator

Cases 1 and 2 meant a naive "token goes in cell [9]" backfill would have written the status
token into a *rating* cell. Case 3 shows the defect is not merely legacy: a careless edit
introduces it today, and only a column-count check catches it.

**Proposed shape.** Add a `cell-count` check to `verify`: flag any row whose cell count does
not equal the ledger's declared column count (10 for the standard preset, 5 for a sprint
ledger). Error severity, since it silently corrupts every downstream column read.

**Bonus.** The same check would catch pipe-bearing content generally, which is the root
cause. Worth pairing with a note in the format spec: escape `|` as `\|`... which is itself
the trap. Recommend the spec advise `grep -E 'a|b'` be written as prose, or the pipe
replaced with an HTML entity, rather than backslash-escaped.

### I1: first-run setup interview

**Status:** Proposal (2026-09-05)

**The gap.** The tool infers per-project facts from the ledger's shape and defaults the rest, silently:
- **Target vocabulary** — release-based (🚢 THIS / NEXT / LATER, ship gate active) vs continuous (Window, no ship gate). `target_is_this` / `blocks_release` branch on this; a wrong guess makes `ship_ready` (added 2.8.1) either meaningless or wrong. This is the one place an interview clearly earns its keep.
- **Ledger set** — one ledger or several siblings. The registry README is hand-maintained; drift there caused real confusion in the 09/05 Stuffolio session about which ledgers gate a release.
- **Budgets / caps** — default char budget vs a per-ledger row cap (the Stuffolio MI sprint ledger runs a hard 15-row cap).

**The change.** A ONE-TIME, three-question setup, fired only when `verify`/`list` runs against a directory with no registry and no ledger (true first use — never on an existing project): (1) release-based or continuous? (2) how many ledgers, and their names? (3) default budgets or set caps? It writes the registry README + `.unforget.json`, then never fires again.

**Scope guardrails (the traps this must dodge):**
- **NOT a big wizard.** unforget's strength is a flat markdown file + a linter; every field it needs already lives in the row. A heavy interview on a friction-reducing tool is the wrong first impression, and mirrors the "interview off by default" stance in the consumer's own INTERVIEW_WORKFLOW.
- **Answers become VISIBLE content, never hidden config.** Write the "release-based" answer into the registry README's declared shape so `verify` re-derives it every run and it cannot silently drift. A config dotfile that lies is worse than none — the exact failure the consumer documented when it deleted `website-sync-config.json` (dormant 1,200 commits while self-reporting `"status": "current"`).
- **Never fires on an existing ledger.** Gate strictly on "no registry AND no ledger."

**Open question before building:** does the skill already have any first-run hook to extend, or would this be net-new plumbing? Check before designing.

**Relation to existing items:** overlaps F4 (auto-derive ship gate) — F4 auto-derives, I1 asks once and records. They are complementary: I1 sets the vocabulary F4 would then derive against.

**Before/after (the person adopting unforget on a new project):** *Before* — they install it, start logging rows, and the tool quietly assumes a shape (release vs continuous, single vs multi-ledger); if the assumption is wrong, `ship_ready` misreports and nobody is told. *After* — first run asks three questions, records the answers as visible registry content, and every later run derives from that recorded shape instead of guessing. No behavior change on an existing ledger (the interview never fires there).
